# Google Play Game Stats v1 design contract

Design baseline: checked-in commit `67f8a5b`, app `4.2.1`, gameplay telemetry schema `2`, progression schema `3`, ruleset `2026.09.1`. Google documentation checked 2026-09-04. Runtime reconciliation: gameplay telemetry now uses schema `3` after the Orders-boundary and reinforcement-success fixes; the Game Stats feature remains unimplemented. This document specifies a future implementation; none exists as a result of this pass.

## 1. Scope and non-goals

Game Stats v1 records player-career facts from **completed Wars**, including wins, losses, and true ties. Retain all ten candidate stats using **one reusable `war_completed` event**. A War is the natural accounting boundary already used by local career statistics. Summarizing its public domain events supplies every proposed aggregation and commander filter without uploading a second detailed combat history.

Lifetime means eligible play recorded after integration becomes available for the signed-in Play Games account. Do not backfill resettable local totals, guest play, Campaign history, or achievements. Restarted, abandoned, or interrupted Wars that never resolve contribute nothing to these ten stats. Local Reset Stats cannot reset Google records or trigger resubmission.

This pass creates no implementation or Play Console artifacts. There is no leaderboard implementation, achievement bridge work, community backend, Hall of Valor redesign, commander dossier redesign, or new gameplay mechanic. No CSVs, ZIPs, icons, Play IDs, Firebase, BigQuery code, or persistent player identifiers are introduced.

Commander records belong in a future Dossier; Hall of Valor remains personal physical-card history; achievements remain named feats. Consented GA4/BigQuery analysis remains the community data path. This contract neither sends Game Stats into GA4 nor promises access to a Google Game Stats raw-event export.

Google currently allows 50 stats; published stats cannot be deleted. V1 uses ten slots, all repetitive stats, and no `progressUpdate`. Treat published names, property meanings, units, filters, and aggregations as permanent product commitments. [Game Stats overview](https://developer.android.com/games/pgs/gamestats), [Console integration](https://developer.android.com/games/pgs/integrate-gamestats).

## 2. Final event schema

### Event boundary and property budget

`war_completed` is emitted once from `GameResolvedEvent` after a genuinely resolved War. The event contains 18 required properties and one conditional property: **19 declared properties total**. No `battle_completed`, `reinforcement_completed`, or `two_ace_resolved` Google events are needed in v1. Their authoritative domain equivalents feed three small in-memory accumulators instead. This is a deliberate simplification of the candidate four-event design, not a separate event per stat.

The Console declaration limit is 20 events and 20 properties per event, stricter than the runtime API's 25-property allowance. Use the declaration limit. All proposed keys meet its naming rules; types below are the literal Google CSV types. [Console schema limits](https://developer.android.com/games/pgs/integrate-gamestats#csv-file-guidelines-for-events), [runtime limits](https://developer.android.com/games/pgs/gamestats#events-request-body).

Only the properties in the following table enter `PlayerGameEvent`. Missing required context invalidates the record; do not substitute a default commander or guess modifiers. Integers must be finite safe integers on the TypeScript side and Java `long` values natively. Validate invariants before submission; never silently clamp a gameplay fact.

Source abbreviations used in the table:

- **Events**: [game-events.model.ts](../src/app/core/models/game-events.model.ts), the typed public event contract.
- **Controller**: [game-controller.service.ts](../src/app/services/game-controller.service.ts), especially `playTurn`, `setupBattle`, challenge resolution, and `finishAtGameOver`.
- **Progression**: [campaign-progression.service.ts](../src/app/core/services/campaign-progression.service.ts) and [progression.model.ts](../src/app/core/models/progression.model.ts).
- **Chapters**: [campaign-chapter.model.ts](../src/app/core/models/campaign-chapter.model.ts).
- **Versions**: deployment environment fields generated by [set-env.js](../scripts/set-env.js); Game Stats schema version is a new constant independent of GA4.

`war_margin` deliberately matches durable Campaign margins and GA4's terminal `attrition_differential`. It is **not** necessarily player remaining minus opponent remaining: an attrition loser can retain undealt cards. Do not copy the table summary's differently computed `warDifferential`.

The adapter also retains the existing random `warId` as a **local transport correlation/deduplication key**, outside Google's custom properties. Do not upload a Campaign ID, card ID, local profile ID, PGS player ID, email, name, hidden rank, dialogue, or raw event log. This event is self-contained for filtering; a Google-side War join is unnecessary.

## 3. Final v1 Game Stat list

Every row uses `war_completed`. `MAX` receives each War's value, never a previously accumulated career maximum. `SUM` receives each War's increment, never a lifetime total. The player-facing meaning column is also the exact proposed default-English stat description. All properties selected for aggregation are numeric; set Console `Unit=UNITLESS`, with the human unit below explained in the description. Set `Good value direction=INCREASING` for all ten: greater is a career record, not a claim of greater skill.

| Display name | Internal/config name | Source event | Aggregation/property | Filter | Human unit | Competitive | Player-facing meaning / default description | Permanent-slot reason |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| Wars Fought | `wars_fought` | `war_completed` | `COUNT(turns)` | None | Wars | No | Wars you have completed, including victories, defeats, and ties. | Career denominator for every dramatic-event frequency. |
| Wars Won | `wars_won` | `war_completed` | `SUM(player_win)` | None | Wars | No | Completed Wars ending in your victory. | Basic outcome history alongside stochastic records. |
| Comeback Victories | `comeback_victories` | `war_completed` | `COUNT(comeback_deficit)` | `comeback_deficit >= 3` | Wars | No | Victories after trailing by at least 3 cards at the start of a turn. | Frequency of reversals, not just the single biggest one. |
| Greatest Comeback | `greatest_comeback` | `war_completed` | `MAX(comeback_deficit)` | None | Cards | **Yes** | Largest turn-start card deficit overcome in victory, counting comebacks of 3 or more cards. | A dramatic personal record appropriate for comparison. |
| Battles Fought | `battles_fought` | `war_completed` | `SUM(battles)` | None | Battles | No | Distinct Battles entered in your completed Wars. Recursive layers count as one Battle. | Measures encounter intensity rather than another win counter. |
| Deepest Battle | `deepest_battle` | `war_completed` | `MAX(deepest_battle)` | None | Layers | **Yes** | Most three-card layers dealt per side in one Battle during a completed War. | Rare recursive escalation, independent of who wins. |
| Longest War | `longest_war` | `war_completed` | `MAX(turns)` | None | Turns | No | Most turns in one completed War. | Measures sustained attrition without rewarding idle time. |
| Reinforcements Sent | `reinforcements_sent` | `war_completed` | `SUM(reinforcements_sent)` | None | Cards | No | Reinforcement cards you committed in completed Wars. | Player action frequency and rescue-success denominator. |
| Successful Reinforcements | `successful_reinforcements` | `war_completed` | `SUM(successful_reinforcements)` | None | Rescues | No | Your reinforcements that won their comparison outright in completed Wars. Ties are excluded. | Measures how often an uncertain intervention immediately worked. |
| Aces Felled by Twos | `aces_felled_by_twos` | `war_completed` | `SUM(aces_felled_by_twos)` | None | Aces | No | Opponent Aces directly defeated by your Twos in completed Wars. | Distinctive rule-driven incidents worth accumulating. |

**No original candidate is rejected or replaced.** The names are retained with exact semantics above. Battles Won, Campaigns Won, Tokens Earned, Achievements Unlocked, and physical-card biography stats remain excluded/deferred; unused capacity is not a reason to add them. Zero MAX inputs are valid completed-War facts, not synthetic initialization events. Before any eligible War, Google may have no value; do not manufacture a War to display zero.

## 4. Commander-analysis compatibility

Use the permanent IDs from [commander.model.ts](../src/app/core/models/commander.model.ts), including the hyphen in `cornered-general`. Property **values** need not follow event/key naming rules. [commander-identity.model.ts](../src/app/core/models/commander-identity.model.ts) maps them to Marcel (`quartermaster`), Edmund (`gambler`), Matthias (`analyst`), Bastien (`attritionist`), and Lorenzo (`cornered-general`). Renaming a character must not change the ID.

The following are future definitions, **not additional permanent v1 slots**. Each simple Google definition needs only the one supported filter:

| Future question | Derivation on `war_completed`, filtering `commander_id = attritionist` |
| --- | --- |
| Wars against Bastien | `COUNT(turns)` |
| Wins against Bastien | `SUM(player_win)` |
| Greatest comeback against Bastien | `MAX(comeback_deficit)` |
| Battles against Bastien | `SUM(battles)` |
| Deepest Battle against Bastien | `MAX(deepest_battle)` |
| Reinforcements and immediate rescues against Bastien | Separate SUMs of `reinforcements_sent` and `successful_reinforcements`. |
| Two-over-Ace incidents against Bastien | `SUM(aces_felled_by_twos)` |

A future local/aggregate consumer can compute W/L/T by `outcome`, win rate as `SUM(player_win)/COUNT(turns)`, Battles per War as `SUM(battles)/COUNT(turns)`, and rescue rate as `SUM(successful_reinforcements)/SUM(reinforcements_sent)`, leaving zero-denominator rates undefined. Median/percentile War length, comeback frequency, and distributions of per-War event counts belong to that consumer, not CSV aggregations. Multiple simultaneous conditions also belong to local/aggregate queries; do not pretend Google's single-filter configuration supports arbitrary SQL.

Keep **difficulty** (`outcome`, `war_margin`) separate from **intensity** (`turns`, `battles`, `deepest_battle`, reinforcements, comebacks, Two-over-Ace incidents). A commander can have ordinary win rates and unusually eventful Wars. This schema preserves per-War intensity; it does not preserve every Battle's depth distribution or every reinforcement opportunity. Existing consented gameplay telemetry is the detailed-analysis path.

Personal records could eventually be accumulated locally by commander and compared with thresholded community summaries from consenting GA4 players. The Game Stats event design supplies compatible meanings, not a community backend or permission to join Google account identity to analytics. Samples will differ: PGS eligibility is not GA4 consent, and completed-War cohorts exclude abandonment.

## 5. Campaign/modifier compatibility

Freeze the future Game Stats adapter's rules context on the **first `turn_started`**, after Campaign Orders have been confirmed and before any reinforcement. Keep that snapshot until the War closes, including War 3. Never read the next Campaign's state after `recordResolvedWar` advances progression. The controller now establishes canonical telemetry and domain `war_started` through `beginWarWhenOrdersReady`, after Orders lock; the first-turn snapshot remains suitable for the proposed adapter's eligibility and starting-reserve inputs.

| `campaign_kind` | `campaign_mode` | `campaign_modifiers` |
| --- | --- | --- |
| `story` | `standard` (Chapter I) | `none` |
| `story` | `limited_reserves` (Chapter II) | `limited_reserves` |
| `story` | `fog_of_war` (Chapter III) | `limited_reserves+fog_of_war` |
| `story` | `total_war` (Chapter IV) | `limited_reserves+fog_of_war+total_war` |
| `custom` | `standard` | Any of the eight canonical stacks below. |

Allowed stacks, in `CAMPAIGN_MODIFIER_ORDER`: `none`; `limited_reserves`; `fog_of_war`; `total_war`; `limited_reserves+fog_of_war`; `limited_reserves+total_war`; `fog_of_war+total_war`; `limited_reserves+fog_of_war+total_war`. Reuse the serializer; never sort alphabetically or use toggle-click order. Post-story play is currently neutral custom play, not replay of an authored Chapter identity. This supersedes older descriptions of replaying individual Chapters in [current-development-status.md](../.github/instructions/current-development-status.md); see the current [alternate-rules contract](alternate-rules-campaigns.md).

Stratify commander comparisons by kind, mode, stack, ruleset, Campaign position, and starting reserves where applicable. Report sample sizes; raw differences do not establish causal commander strength. `reserves_at_war_start` prevents five available reserves and none available from appearing equivalent. The three-War position is retained without uploading Campaign IDs or schedules to every record. AI tuning changes require a new `ruleset_version`, even when the physical rules stay the same.

Tokens are verified progression/economy: `summarizeCampaign` requires exactly three resolved Wars; Campaign victory awards `1 + (differential > 0 ? 1 : 0)` tokens, defeat/draw zero. Under Total War a victory necessarily has positive differential and awards two. Other Campaign victories can award one or two. `recordResolvedWar` updates the durable balance and lifetime earned only at Campaign completion; purchases update lifetime spent. These live in `CampaignProgression`, separate from resettable `GameStatistics`. Tokens are not awarded after Battles and are not a substitute for Campaign Wins.

## 6. Competitive bounds

Published competitive intent is **yes** for Greatest Comeback and Deepest Battle only. Separate a proved outer bound from proof that its endpoint is attainable, and separate a score bound from a throughput/rate limit.

| Stat | Mathematically valid minimum | Maximum analysis | Proposed score-domain envelope |
| --- | --- | --- | --- |
| Greatest Comeback | `0` from a completed War without a qualifying comeback. Smallest positive qualifying value is `3`, matching the modest threshold. | **Proved outer bound `25`; exact attainable winning maximum remains unproved.** Each side owns at most 26 cards. At a sampled turn both draw successfully, leaving reserves between 0 and 25. Their difference is therefore at most 25. Recoverability with particular surviving ranks can impose a tighter maximum. | `0..25`, if Google accepts a conservative allowable-score envelope. Do not label 25 an attainable comeback record. |
| Deepest Battle | `0` when no Battle layer was dealt; smallest positive value `1`. | **Exact maximum `8`.** Each side stakes at least its initial card, then three new cards per layer: `1 + 3d <= 26`, so `d <= 8`. A reinforcement costs one extra card on one side and cannot raise the bound. | `0..8`. |

Deepest Battle attainability: arrange the two legal color decks with matching initial ranks and matching chosen champions through seven layers; all those cards remain staked. An eighth three-card layer is still available on both sides. It can resolve decisively or tie with equal remaining reserves. The latter ends the War in a true tie but still reaches depth eight. No ninth layer is dealt. [Deck construction](../src/app/core/models/deck.model.ts), [Battle commitment and conservation](../src/app/core/services/game-state.service.ts), [recursive/attrition resolution](../src/app/core/services/turn-resolution.service.ts).

To establish the **tight** Greatest Comeback maximum, analyze reachable 52-card rank/suit allocations under bottom-of-deck return order, one reinforcement per turn, unchallengeable Two-over-Ace, and the immediate insufficient-Battle-reserve outcomes. Produce a legal full-War witness for the largest recoverable sampled deficit plus an impossibility argument for larger deficits. A partial fixture with invented decks is insufficient. This remains bounded rules analysis, not a reason to invent a 52-card or percentile cap.

The `turns <= 51` validation envelope is conservative, not a claimed attainable Longest War record: each continuing ordinary turn permanently removes at least one card, recursion stays within that turn, and at least two cards must exist to start the last turn. Thus at most 50 earlier casualties/turns plus the terminal turn. No published hourly rate is inferred from this; animations can be skipped and player thinking time varies.

**Artifact gate:** Google's [overview](https://developer.android.com/games/pgs/gamestats#integration-steps) describes competitive bounds as hourly limits, whereas its [CSV field reference](https://developer.android.com/games/pgs/integrate-gamestats#repetitivestatsconfigcsv-format) describes allowable scores. Before filling competitive `Min limit`/`Max limit`, confirm how these apply to MAX stats, including zero/no-positive-record cases and whether conservative outer bounds are accepted. If they are score envelopes, use the values above. If they require hourly increments, obtain the corresponding documented MAX semantics; do not reuse score bounds as a guessed rate. Keep both competitive flags as designed while this external configuration question is resolved.

## 7. Mapping to authoritative events and delivery

### Domain projection

Use a new application service subscribed eagerly to [GameEventBusService](../src/app/services/game-event-bus.service.ts), as telemetry is eagerly constructed in [app.ts](../src/app/app.ts). The bus is synchronous and non-replaying. Keep the mapper pure; never read `presentedTurn`, a dialog summary, animation state, Chronicle text, or Hall of Valor to derive these values.

| Input / seam | Mechanical projection |
| --- | --- |
| Controller `beginWarWhenOrdersReady`, immediately after obtaining the existing random `warId` | Call the new service's `beginWar(warId)`; reset its accumulators. This is a future integration hook, not a change to domain event semantics or GA4. |
| First `turn_started` | Freeze actual Progression commander, Campaign kind/mode/modifiers/index/reserves and release versions. Require selected Orders. Lock eligibility and the current local-profile/authentication epoch. Later turns cannot replace this context. |
| `battle_started`, `battle_layer_added` | Accumulate `deepest_battle = max(previous, layerRound)`, initially zero. Do not count `battle_continues` as a newly dealt layer. |
| Human `challenge_resolved` | Increment successful reinforcements only for `comparison=PLAYER_WINS`. Use the comparison result; corrected `challengerWon` now has the same direct-win meaning. Terminal `winner` remains separate. |
| `clash_resolved` | Increment Aces felled iff the authoritative comparison is `PLAYER_WINS`, `specialRule=true`, player's card is TWO, and opponent's card is ACE. |
| `challenge_resolved` from either side | Orient the pair by `challenger`: human challenger uses reinforcement vs original winner; opponent challenger uses original winner vs reinforcement. Increment Aces felled iff the oriented human TWO defeats the opponent ACE with `comparison=PLAYER_WINS`. Never include `originalBeatenCard` as the newly compared card. |
| `battle_cards_revealed` | Use `event.selection` exclusively: increment Aces felled iff its comparison is `PLAYER_WINS`, special rule is true, and the human/opponent selected ranks are TWO/ACE. |
| `game_resolved` | Copy outcome, turns, battles and human reinforcements; derive `player_win`, `comeback_deficit`, and `calculateWarMargin`; attach the three accumulated values and the frozen context. Emit at most one `war_completed` for this War. Close before accepting a duplicate terminal event; preserve a newly started War on reentrant/nested events. |
| `game_abandoned`, replacement, profile change, local deletion, authentication/channel loss | Discard the unfinished War's accumulator and invalidate eligibility. A later sign-in/reconnect starts eligibility with the next War, never reconstructs this War. Visibility alone is not abandonment. |

The three aggregate values `deepest_battle`, `successful_reinforcements`, and `aces_felled_by_twos` are **not fields of the current `GameResolvedEvent`**. They are nevertheless authoritatively derivable from the public events above; the future adapter needs three counters, not new durable career state or new domain events. `campaign_kind` and starting-reserve snapshot are also new projections of existing Progression state. All other metric inputs already exist on the terminal event. No v1 metric requires unavailable hidden information.

Relevant edge cases:

- `enterBattle` can resolve attrition before the first layer: it emits no `battle_started`, and the normal controller path leaves `battlesCount=0`. An immediate tied clash is not automatically one dealt Battle.
- A Battle with layers can end in a **true terminal tie without `battle_resolved`**. The `battlesCount` terminal field and layer accumulator retain its count/depth. Counting only `battle_resolved` would lose it.
- Controller `deepestBattleLayer` is advanced before `dealBattleLayer`; its exceptional failed-deal branch can record an attempted layer. This contract requires successful dealt-layer events, never attempted commitments.
- On a reinforcement tie, `resolveAttrition` can return a winning side even though `comparison=TIE`. The runtime now derives `challengerWon` and local successful-challenge counters from the comparison alone. Domain `escalatedToBattle` distinguishes a tie entering Battle from immediate attrition, including a true terminal tie. This now agrees with the Game Stats direct-win definition; historical saved totals are not rewritten.
- Two-over-Ace comparisons cannot be challenged. Count their direct comparison once; do not count it again through `battle_resolved`, `settlement_resolved`, or individual casualties. A Two winning a Battle against another rank does not directly fell collateral Aces.
- `comeback_deficit` uses the Controller's maximum sampled immediately after the two ordinary cards are drawn. Equal draws preserve the turn-start army difference; transient challenge/Battle reserve differences are not sampled. A 1- or 2-card recovery is zero here, and the 15-card achievement threshold is unrelated.

### Platform and ownership contract

[PlatformAchievementsService](../src/app/core/services/platform-achievements.service.ts) accepts an explicitly registered `VerifiedTwaTransport`; [MainActivity](../android/app/src/main/java/com/cboler/warofattrition/MainActivity.java) initializes Play Games but registers no verified channel or response callback. Native achievement sync is therefore not operational end to end. Preserve the boundary described in the [Play Store bridge documentation](play-store/README.md#native-play-games-bridge-status); a URL flag, arbitrary `window.message`, or WebView interface is not authorization/readiness.

The future implementation uses a separate `PlatformGameStatsService` and native `PlayGameStatsBridge` wrapper, sharing only the future verified host transport and native authentication lifecycle. Do not refactor or reconcile achievements. The currently pinned [Android dependency](../android/app/build.gradle) is `play-services-games-v2:20.1.2`; use `22.0.0` for this integration, which added `GameStatsClient` and `PlayerGameEvent`. [Official SDK release notes](https://developers.google.com/android/guides/releases#july_29_2026).

Extend the [typed bridge protocol](../src/app/core/models/twa-bridge.model.ts) additively with these Game Stats messages, still protocol `v1`:

| Direction | Type | Fields / meaning |
| --- | --- | --- |
| Web → native | `GAME_STATS_INIT` | Requests Game Stats capability and current native authentication status. |
| Native → web | `GAME_STATS_READY` | `available` and `signedIn` booleans. Emit updated status on authentication changes. No account identifier. |
| Web → native | `RECORD_GAME_STATS` | Existing local `warId` correlation key and exactly one `war_completed` property map from section 2. |
| Native → web | `GAME_STATS_BUFFERED` | `warId`; wrapper invoked the SDK's local recording API. This is **not** a server acceptance acknowledgement. |
| Native → web | `GAME_STATS_REJECTED` | `warId`; enumerated reason `invalid_payload`, `unavailable`, or `signed_out`. Never include raw account data. |

Record only real production gameplay with an authenticated, capable, verified native session at the first turn and at completion. Web/PWA, unsigned/unavailable transport, tests, screenshot fixtures and rule demos are no-ops. GA4 measurement configuration and analytics consent do not gate PGS career stats; they continue to gate anonymous analytics separately. Never send analytics identifiers to PGS or PGS identifiers to GA4. A local profile switch invalidates the in-progress record; it cannot transfer someone else's unfinished War into a signed-in career.

No durable web outbox or retrospective reconciliation is added in v1. Once eligible, send the completed record once. Native validates the exact whitelist/types and rejects duplicates by `warId` within the active host session, builds one `PlayerGameEvent`, and calls `PlayGames.getGameStatsClient(activity).recordEvent(event)` followed by `requestEventsUpload()`. SDK buffering owns offline upload/retry. A lost bridge receipt must not cause construction of another event; do not promise exactly-once cloud delivery or retry a lifetime total. A native crash before handoff can lose that War, and reconnect does not backfill it.

These methods return `void`, not an achievement-style `Task`; `GAME_STATS_BUFFERED` cannot be called “synced.” The Java builder exposes typed `addProperty` overloads, not an app-supplied event-ID setter. Keep `warId` outside the Google property map and do not invent such an SDK method. [GameStatsClient reference](https://developers.google.com/android/reference/com/google/android/gms/games/GameStatsClient), [PlayerGameEvent.Builder reference](https://developers.google.com/android/reference/com/google/android/gms/games/playergameevent/PlayerGameEvent.Builder).

Only aggregate scalars leave the app at completed-War time. This respects Fog's active-War history seal without a second delayed-event queue or copying GA4's card redaction machinery. Transport establishment remains an **external integration prerequisite**, not work authorized by this contract.

## 9. Telemetry consistency finding

This finding incorporates the subsequent documentation correction and runtime fixes. Game Stats itself remains a design contract.

**Commander placement:** [telemetry-schema.md](telemetry-schema.md#common-event-parameters) now correctly documents boundary-only `commander_id`. The [mapper](../src/app/services/game-telemetry.mapper.ts) `commonParameters` contains ten fields including `turn_number` and omits commander. It adds commander for `war_resolved` and `war_abandoned`; [GameTelemetryService](../src/app/services/game-telemetry.service.ts) includes it in canonical `war_started`. `TelemetryEnvelope.commanderId` in the [model](../src/app/core/models/telemetry.model.ts) does not make it a common emitted parameter.

**Parameter pressure:** with all non-Fog card fields present, current mapper counts are:

| Record | Parameters | With commander added to common parameters |
| --- | --- | --- |
| Clash `comparison_resolved` | 24 | 25 |
| Battle `comparison_resolved` | 25 | 26 |
| `battle_resolved` with selection | 25 | 26 |
| `reinforcement_resolved` | 25 | 26 |

[normalizeTelemetryRecordForGa4](../src/app/services/telemetry-transport.service.ts) rejects an entire record over 25 parameters; it does not trim the last field. Casually adding commander would therefore lose rich records and their join keys. **Recommendation: retain normalized `war_id → commander/context` joins as the canonical GA4 method and correct the documentation's blanket common-field claim in a separate focused documentation change.** In this contract, section 2 exclusively describes PGS, where the one self-contained event always carries commander and remains under its declaration limit.

Build the analytics War dimension primarily from `war_started`, with terminal context as a consistency check/fallback. Do not silently guess attribution for missing or conflicting context; exclude or mark unattributed. Consent is locked at a War boundary, withdrawal stops collection, and transport failure can still leave gaps. `campaign_resolved` carries three indexed commander IDs, not a single commander for the entire Campaign. `cosmetic_unlocked` has no War ID or commander, so “all records carry war_id” is also too broad outside game-bus records.

**Orders-boundary correction (gameplay schema 3):** [TableGame](../src/app/table-game/table-game.ts) may prepare the decks before Campaign Orders, but Controller `replaceGame` now leaves the War start pending while Orders are unselected. `beginWarWhenOrdersReady` freezes the final schedule/modifiers exactly once after confirmation, called by `ensureGameStarted` and guarded by `playerDrawCard`. Already-ordered Wars start immediately; new Campaigns wait for Orders. This fixes commander attribution and Fog redaction without a corrective start or fake restart.

Canonical start, terminal events and progression retain one War ID. Mid-War consent grants still wait for the next boundary. Historical schema-2 War 1 records can share stale context at both ends and cannot be assumed repaired by a War-ID join. The future Game Stats first-turn snapshot remains valid, but no longer needs to work around an unfixed runtime sequencing defect.

**Reinforcement semantics (gameplay schema 3):** the mapper emits `success`/`failure` only for outright comparisons, `battle` for a tie entering Battle, and `tie` for immediate attrition. The domain escalation flag populates the existing `escalated_to_battle` parameter without exceeding 25 fields. Local rescue statistics, achievements and Hall records consume corrected direct-win `challengerWon`; Chronicle text preserves tie/attrition meaning. Use schema 3 or later for community-rate comparisons; older events and saved totals are not rewritten. UI schema remains 1 and ruleset `2026.09.1` because no engagement or game rules changed.
